# 装修设计 Agent 分阶段向导重设计

## 1. 背景

当前项目页把上传户型、风格预算、Agent 追问、方案生成和结果预览全部堆在一个页面中。这个结构适合工程 MVP 验证接口，但不像一个面向业主的装修设计产品：用户会看到太多同时存在的表单和按钮，也需要手动点击“获取下一步问题”“生成方案”“生成效果图”“生成 PDF brief”。

本次重设计将产品改为分阶段向导。用户每次只面对一个任务，系统根据项目状态自动进入下一阶段。中间保留一个“设计师追问”阶段，但它不是问卷，而是由设计师 Agent 主动提出空间想法、改造可能性和需求探索问题，再根据用户回答继续追问或进入生成。

## 2. 设计目标

- 让装修小白感觉自己被设计师带着走，而不是在操作后台表单。
- 每个阶段只展示当前任务，减少认知负担。
- 系统自动推进流程，不要求用户手动拉取下一问或手动依次生成方案、效果图、PDF。
- 最终结果沉淀为一个可反复访问的方案页，而不是 JSON 预览。
- 保留 MVP 技术边界：输出装修前沟通 brief，不输出 CAD、施工图、正式报价或采购清单。

## 3. 页面结构

采用“严格分阶段路由 + 最终方案页”的结构：

- `/`：创建项目。
- `/projects/[projectId]/upload`：上传户型图。
- `/projects/[projectId]/analysis`：确认户型分析。
- `/projects/[projectId]/preferences`：选择风格、预算档位并补充自然语言需求。
- `/projects/[projectId]/interview`：设计师追问。
- `/projects/[projectId]/generating`：生成方案、效果图和 PDF brief。
- `/projects/[projectId]/brief`：最终方案页。

每个阶段有独立 URL，可以刷新恢复。页面进入时根据项目状态校验访问是否合法；如果用户打开了过早或过晚的阶段，系统应重定向到当前应完成的阶段或最终方案页。

## 4. 阶段设计

### 4.1 创建项目

首页只承担创建项目的任务。用户输入项目名称后创建 Project，并进入上传户型图页面。

首页需要传达产品定位：这是帮助业主整理装修需求和方案 brief 的 AI 设计师，而不是专业施工图工具。

### 4.2 上传户型图

上传页只展示户型图上传任务。用户选择图片并提交后，系统自动调用户型分析接口。

上传成功后页面进入分析中状态，展示简短进度文案，例如“正在识别房间、采光和空间关系”。分析完成后自动跳转到确认分析页。

失败时保留已选文件或提示重新上传，不丢失项目。

### 4.3 确认户型分析

确认分析作为独立阶段保留。原因是户型理解直接影响后续方案，用户需要有机会确认或修正 AI 的理解。

页面展示结构化摘要，而不是 JSON：

- 识别到的主要空间。
- 可见房间标注或尺寸信息。
- 大致空间关系。
- 采光、动线、收纳或布局问题。
- AI 不确定、需要用户确认的信息。

用户确认后进入风格预算页。MVP 可以先支持简单的文本修正；后续可扩展为逐项编辑。

### 4.4 风格与预算

该页让用户选择一个预设风格、一个预算档位，并用自然语言补充需求。

预设风格继续使用现有范围：原木风、中古风、现代简约、奶油风、侘寂风。预算档位继续使用经济型、品质型、高品质型。

提交后保存 PreferenceProfile，并自动进入设计师追问页。

### 4.5 设计师追问

设计师追问阶段是本次重设计的核心。它不再要求用户点击“获取下一步问题”。进入页面后，系统自动请求第一条设计师发言。

第一条发言应由设计师 Agent 主动开场，基于户型分析、风格、预算和用户偏好提出空间想法或需求探索问题。例如：

> 我看这个户型有一个次卧空间，如果平时不常住人，可以考虑做成多功能书房，兼顾临时客房和收纳。你们对这个房间有什么明确需求吗？

或者：

> 客餐厅和阳台关系比较近，我会优先考虑采光和显大。你们有没有特别在意的生活场景，比如孩子活动区、朋友聚餐、投影观影、宠物活动？

用户回答后，系统自动判断下一步：

- 如果用户提出明确需求，继续围绕该需求追问细节。
- 如果用户表示没想法，设计师给出 2-3 个可选方向。
- 如果某个空间有明显机会点，设计师主动提出改造建议。
- 如果某个选择影响预算或落地风险，设计师说明取舍并询问是否接受。
- 如果信息足够，设计师总结将采用的方向，并自动进入生成页。

追问最多 12 轮，但不强行问满。Agent 返回完成状态后，前端自动跳转到 `/generating`。

视觉上，追问页不是普通聊天软件。推荐布局是左侧为设计师当前问题、回答区和对话历史，右侧为固定摘要，包括户型摘要、风格预算、已确认需求、已采纳建议和追问进度。

### 4.6 生成中

生成中页面自动串联后续任务，不再要求用户手动点击“生成方案”“生成效果图”“生成 PDF brief”。

页面展示以下步骤：

- 正在整理需求画像。
- 正在生成整体设计策略。
- 正在生成重点空间方案。
- 正在生成效果图。
- 正在生成 PDF brief。

每一步有明确状态：等待中、进行中、完成、失败可重试。全部完成后自动跳转到最终方案页。

如果某一步失败，页面应说明失败原因并提供重试入口。已完成步骤不应重复执行，除非用户主动要求重新生成。

### 4.7 最终方案页

最终方案页是长期可访问的结果页。它应像一份轻量设计 brief，而不是后台数据面板。

页面内容包括：

- 顶部信息：项目名、风格、预算档位、PDF 下载入口。
- 方案概览：一句话设计方向和 3-5 条关键策略。
- 户型分析摘要：空间、采光、动线、注意点。
- 需求摘要：居住成员、生活习惯、用户偏好、已采纳设计建议。
- 重点空间方案：每个空间一张效果图、设计目标、布局建议、配色材质、家具软装、预算取舍、落地注意事项。
- 风险与边界：说明该文件是装修前沟通 brief，不是施工图或正式报价。
- 后续动作：重新生成效果图、重新进入追问、下载 PDF brief。

方案页不得展示原始 JSON。结构化数据应转为业主可读的文案、列表和图文模块。

## 5. 状态与自动跳转

项目状态仍然是流程控制的核心。前端页面应根据状态决定用户当前可访问的阶段。

推荐状态流：

```text
CREATED
-> FLOOR_PLAN_UPLOADING
-> FLOOR_PLAN_ANALYZING
-> FLOOR_PLAN_ANALYZED
-> ANALYSIS_CONFIRMED
-> PREFERENCES_COLLECTED
-> INTERVIEWING
-> INTERVIEW_COMPLETE
-> GENERATING_PLAN
-> PLAN_READY
-> GENERATING_RENDERINGS
-> RENDERINGS_READY
-> GENERATING_BRIEF
-> BRIEF_READY
```

现有状态可以复用或渐进扩展。实现时不要求一次性引入所有中间状态，但必须保证页面能够知道“下一步应该去哪里”。

## 6. 组件边界

建议拆分现有 `ProjectWorkspace`，避免继续维护一个过大的全流程组件。

推荐组件：

- `ProjectShell`：项目页通用外壳，包含阶段进度、项目名、状态提示。
- `StepProgress`：阶段进度显示。
- `UploadStep`：上传户型图。
- `AnalysisReviewStep`：户型分析确认。
- `PreferencesStep`：风格预算和自然语言需求。
- `InterviewStep`：设计师追问。
- `GenerationStep`：生成进度和重试。
- `BriefPage`：最终方案展示。
- `BriefSection` 或同类小组件：展示重点空间、需求摘要、风险边界等。

这些组件通过 API 获取和提交对应阶段的数据，不共享一个巨大的本地状态对象。跨阶段数据由数据库中的 Project 及其关联实体持久化。

## 7. API 行为调整

现有 API 可以继续作为基础，但行为需要调整：

- `/api/projects`：创建项目后跳转上传页。
- `/api/projects/[projectId]/floor-plan`：上传并分析户型图，完成后项目进入户型已分析状态。
- `/api/projects/[projectId]/analysis`：新增或扩展，用于保存用户确认或修正后的户型分析。
- `/api/projects/[projectId]/preferences`：保存偏好后进入追问阶段。
- `/api/projects/[projectId]/agent/respond`：进入追问页时可用空回答或显式 start 动作获取设计师开场；用户回答后返回下一条设计师发言或完成状态。
- `/api/projects/[projectId]/generate`：推荐新增编排接口，用于在生成页自动串联方案、效果图和 PDF brief；也可以先由前端按顺序调用现有 design-plan、renderings、brief 接口。

`agent/respond` 返回内容应支持设计师建议和需求探索，不应只返回简单 question/options。建议返回结构包含：

- `type`: `designer_prompt`、`suggestion`、`complete`。
- `message`: 设计师自然语言发言。
- `options`: 可选项，可为空。
- `recommendation`: 专业建议，可为空。
- `adoptionPrompt`: 是否询问采纳建议。
- `progress`: 当前追问轮次和上限。

## 8. 错误处理

- 上传或分析失败：用户留在上传页，可重试。
- 户型分析不确定：在确认分析页明确标注，不自动跳过。
- 偏好保存失败：保留用户输入。
- 追问接口失败：保留当前对话，允许重试上一次提交。
- 生成失败：生成页显示失败步骤，允许只重试失败步骤。
- PDF 生成失败：方案页仍可展示网页 brief，并提供重新生成 PDF 的入口。

## 9. 测试范围

需要覆盖以下行为：

- 新项目创建后进入上传页。
- 上传户型图后自动进入确认分析页。
- 确认分析后进入风格预算页。
- 保存偏好后进入设计师追问页。
- 追问页加载时自动出现设计师开场。
- 用户回答后自动追加下一条设计师发言。
- Agent 完成后自动进入生成页。
- 生成完成后进入最终方案页。
- 最终方案页不展示 JSON，展示业主可读的方案内容。

## 10. 非目标

本次重设计不包含：

- CAD 级户型编辑。
- 施工图、水电图、正式报价或采购清单。
- 真实 3D 漫游。
- 设计师后台。
- 用户账号体系。
- 支付或商业化流程。

这些能力可以在后续版本中独立设计。
