# Deck It 移动端 Web 适配设计

## 1. 背景

当前系统已经有一套可用的 PC 端项目流程，但页面结构和信息密度明显偏桌面，不适合手机端浏览与操作。现阶段目标不是重写业务流程，而是在保持现有 PC 端流程、状态流转、接口语义不变的前提下，为核心链路补齐移动端 Web 体验，并让手机端视觉与节奏更接近参考图。

已确认的方向如下：

- 业务流程严格沿用现有 PC 端逻辑，不新增业务步骤。
- 首页保留当前深色品牌感。
- 流程页统一切换为浅色背景、白色卡片、蓝色主按钮的轻量工作流风格。
- 移动端采用“单列主画布 + 底部固定主按钮”的主结构。
- 改造范围覆盖完整主链路：首页、上传、分析中、分析确认、风格预算、设计师追问、确认页、支付页、生成中、完成页。

## 2. 目标与非目标

### 2.1 目标

- 让手机端完整走通创建项目到方案完成的主流程。
- 让每一步在手机端只突出一个主任务，减少左右栏压缩带来的信息拥挤。
- 尽量贴近参考图的视觉层级和流程感，但不破坏当前业务实现。
- 保持 PC 端可用，并尽量通过响应式改造复用已有组件与状态逻辑。

### 2.2 非目标

- 不改项目状态机和路由含义。
- 不新增支付、追问或生成相关接口。
- 不把手机端做成与 PC 端完全不同的一套业务体验。
- 不在本次设计里重做最终方案页的信息架构，只处理其移动端可读性和操作可达性。

## 3. 现有流程与移动端目标流程

当前应保持一致的业务顺序为：

`首页 -> 上传 -> 分析中 -> 分析确认 -> 风格预算 -> 设计师追问 -> 确认继续生成 -> 支付页 -> 生成中 -> 完成页`

说明：

- “确认页”沿用现有 `transition` 页职责，本质是追问完成后的生成确认，不扩展为新业务摘要页。
- 支付成功后才进入生成中。
- 完成页仍作为结果完成态，不与最终方案详情页混淆。

## 4. 设计原则

### 4.1 手机端优先

流程页全部按 375px 左右宽度优先设计，再向更大断点自然放宽。桌面端保留现有大体布局能力，但不再作为主设计出发点。

### 4.2 一屏一个任务

每个页面都要有清晰的主任务：

- 上传页：选图并进入分析。
- 分析确认页：确认识别结果。
- 风格预算页：做出偏好选择并补充需求。
- 追问页：持续回答设计师问题。
- 支付页：完成付款或继续支付。

辅助摘要、说明和次要操作都要降级到次级卡片或折叠区域，避免和主任务竞争。

### 4.3 PC 流程不变，手机承载方式重排

同一页面在移动端允许改变信息顺序、卡片层级和按钮位置，但不改变：

- 跳转逻辑
- 表单字段语义
- 主按钮含义
- 后端请求时机

### 4.4 视觉语言统一

- 首页继续使用深色沉浸式品牌风格。
- 流程页采用浅色背景、白色高圆角卡片、蓝色主按钮、低饱和分割线。
- 所有流程页共享一致的顶部步骤条、卡片间距、按钮高度和底部安全区。

## 5. 全局布局方案

### 5.1 首页

- 保留深色 hero 作为品牌入口。
- 移动端改成纵向首屏，不再依赖大宽度左右分栏。
- 品牌、主标题、说明文案在上半区。
- 能力标签改成 2 列或可换行的轻量功能宫格。
- 创建项目卡片下沉到首屏下半区，确保在手机上打开即能完成输入与提交。

### 5.2 流程页壳子

除首页外，上传、分析、偏好、追问、确认、支付、生成、完成共用一套移动端流程壳子。

结构为：

1. 顶部品牌栏
2. 当前步骤标题与简短说明
3. 横向步骤进度条
4. 主内容单列卡片区
5. 底部固定主操作区

其中：

- 顶部步骤条允许横向滚动，不强行压缩 6 个步骤到一行。
- 主操作区固定在屏幕底部，带安全区内边距。
- 主内容区域需要预留底部空间，避免被固定按钮遮挡。

### 5.3 顶部步骤条

步骤仍保持现有 6 步定义：

- 上传户型图
- 户型分析
- 风格预算
- 设计师咨询
- 生成中
- 方案完成

移动端展示规则：

- 当前步骤优先居中可见。
- 已完成步骤显示蓝色勾选。
- 当前步骤显示蓝色高亮。
- 未完成步骤显示浅灰。
- “户型分析”同时覆盖分析中与分析确认两个状态。
- 支付页和确认页仍归在“生成中”这一大步骤体系内，以保持现有状态映射一致。

## 6. 页面级设计

### 6.1 首页 `/`

移动端结构：

- 顶部品牌标识与简短副标。
- 主标题压缩成两到三行，保留“AI 设计师”和“装修前沟通”核心表达。
- 能力入口改成 2 列图标卡片，减少横向拥挤。
- “已帮助 1000+ 业主”这类信任信息做成单独摘要卡，置于创建卡片前后均可。
- 创建项目卡片采用高对比主按钮，表单在首屏即可完整呈现。

交互保持不变：

- 输入项目名。
- 提交后创建项目并跳转上传页。

### 6.2 上传页 `/upload`

移动端结构：

- 顶部步骤条显示“上传户型图”当前状态。
- 主卡片为大尺寸上传区，优先展示图标、标题、支持格式说明。
- 上传建议单独作为次级卡片放在下方。
- 主按钮固定在底部，文案为“选择图片”。

交互保持不变：

- 仍然通过文件选择后立即进入分析中。
- 不新增额外确认步骤。

### 6.3 分析中 `/analysis/loading`

移动端结构：

- 中央展示识别图形、进度条和百分比。
- 任务列表收为单列紧凑卡片。
- 页面整体更偏“处理中反馈页”，避免出现大面积空白。

交互保持不变：

- 自动轮询与跳转逻辑不变。
- 出错时仍展示错误信息，并允许用户返回上一步重新上传。

### 6.4 分析确认 `/analysis`

移动端结构：

- 户型图主卡片放在最上方，优先保证可见面积。
- 分析摘要卡片放在户型图下方。
- 修正输入框作为第三块卡片。
- 底部固定主操作区放“确认并继续”，次按钮“跳过，确认无误”保留但视觉降级。

交互保持不变：

- 提交用户修正后进入风格预算。

### 6.5 风格预算 `/preferences`

移动端结构：

- 风格卡片改成 2 列卡片网格或横向滑动卡组，优先保证点击面积。
- 预算卡片改成纵向堆叠或紧凑 3 卡布局，保证选中态明显。
- 多行补充需求输入框放在页面后半部分。
- 底部固定按钮为“保存并继续”。

交互保持不变：

- 仍提交风格、预算和自然语言需求。
- 不扩展额外字段。

### 6.6 设计师追问 `/interview`

这是移动端改造的重点页面。

移动端结构：

- 聊天区作为主屏内容，占页面最大高度。
- 项目摘要从侧栏改为可折叠摘要卡，默认只展示：
  - 户型
  - 风格
  - 预算
  - 追问进度
- 快捷选项放在输入框上方，以按钮流形式展示。
- 输入框与发送按钮固定在底部。

交互保持不变：

- 首次进入自动触发设计师发言。
- 用户自由输入或点击快捷选项。
- 提交后展示等待态。
- 追问完成后进入确认页，再去支付页。

体验要求：

- 聊天气泡在手机端要保留明显的角色区分。
- 输入框固定时不能遮挡最后几条消息。
- 页面滚动应以聊天内容为主，而不是整页抖动。

### 6.7 确认页 `/transition`

移动端结构：

- 页面定位为“确认开始生成前的过渡确认”，不承担复杂摘要职责。
- 居中展示确认标题、简短说明和两个操作按钮。
- 主按钮固定在底部，文案保持现有含义。
- 次按钮保留“稍后再说/取消”能力。

交互保持不变：

- 继续后进入支付页。
- 取消后回退到既有 fallback 路径。

### 6.8 支付页 `/payment`

这是移动端第二个重点页面。

移动端结构：

- 价格与状态摘要前置，用户进入页面先看到应付金额和当前支付状态。
- 联系方式与优惠码表单置于中段。
- 刷新支付状态作为次级按钮。
- 主支付按钮固定在底部。
- 如果已拥有可用生成次数，则主按钮切换为“开始生成”。

交互保持不变：

- 订单准备、报价刷新、拉起支付、轮询当前订单、支付成功后进入生成逻辑均不变。

体验要求：

- 支付按钮必须始终在首屏可达范围内。
- 输入框聚焦时要避免被固定底栏遮挡。
- 支付处理中状态要清楚显示，避免用户误以为按钮失效。

### 6.9 生成中 `/generating`

移动端结构：

- 上方为生成主状态卡，展示当前阶段、预计等待感知和加载视觉。
- 下方为任务清单卡片，按当前生成阶段展示完成、进行中、等待中状态。
- 预览图如有可展示内容，则放在状态卡下方。

交互保持不变：

- 不新增人工操作。
- 保留自动跳转到完成页的现有逻辑。

### 6.10 完成页 `/complete`

移动端结构：

- 顶部先展示“方案已完成”的完成感和主效果图。
- 下方展示三张结果卡：设计方案、效果图、PDF brief。
- “重新进入追问”“重新生成方案”作为次级操作。
- “下载 PDF brief”作为更强的主操作，可固定在底部或置于结果卡后紧邻区域。

交互保持不变：

- 保留重新追问与重新生成。
- 保留下载 PDF brief。

## 7. 组件与实现策略

### 7.1 `WizardShell`

`WizardShell` 需要升级为真正的响应式流程壳子：

- 支持移动端顶部品牌栏与步骤条。
- 支持页面说明文案插槽。
- 支持底部固定操作区插槽。
- 自动为内容区增加底部留白，避免固定按钮遮挡。

PC 端在中大屏下仍可继续使用现有大画布风格，但布局节奏要向移动端统一。

### 7.2 各步骤组件

各页面优先通过以下方式改造，而不是重做逻辑：

- 调整 DOM 顺序
- 合并或拆分卡片层级
- 折叠侧栏摘要
- 新增移动端专用样式分支
- 将主按钮下沉到固定底栏

避免的做法：

- 复制一整套移动端页面组件
- 为同一业务步骤维护两套请求逻辑
- 在移动端引入不同的状态判断分支

### 7.3 UI 基础样式

需要统一补充：

- 移动端页面左右安全边距
- 卡片圆角与阴影等级
- 按钮高度、底栏高度和安全区
- 表单控件聚焦态
- 长列表与聊天页的滚动行为

## 8. 错误处理与边界情况

- 上传失败、分析失败、支付失败都必须在手机端保持明确可见的错误提示。
- 固定底栏存在时，键盘弹出不能遮挡主要输入区。
- 当项目状态与当前页面不匹配时，移动端仍遵循现有重定向规则。
- 用户刷新追问页、支付页、生成页后，不应因为移动端布局变化破坏既有恢复逻辑。

## 9. 测试策略

### 9.1 手工验证

至少验证以下宽度：

- 375px
- 390px
- 430px
- 768px
- 1280px

重点验证：

- 首页首屏可完整创建项目。
- 上传到完成主流程在手机宽度下都能走通。
- 固定底部按钮不遮挡表单和聊天输入。
- 追问页消息滚动、输入、快捷选项行为正常。
- 支付页支付按钮、刷新状态、支付完成后的跳转清晰可达。
- PC 端原有流程不回归。

### 9.2 自动化回归

优先为以下关键节点补充或更新 E2E 断言：

- 手机视口下的主流程访问与按钮可见性。
- 追问完成后进入确认页，再进入支付页。
- 支付成功后进入生成中。
- 完成页关键操作存在且可触发。

## 10. 实施范围建议

建议按以下顺序实施：

1. 先改全局流程壳子和基础样式。
2. 再改首页、上传、分析中、分析确认、风格预算这些静态结构更强的页面。
3. 最后改追问页、支付页、完成页这几个交互更复杂的页面。

这样能先建立统一的移动端框架，再处理高风险页面，减少反复返工。
